    Trading Setup¶

    swarmd can connect to an Interactive Brokers (IBKR) account and let agents read market data and place orders through a safety layer that enforces caps and mandatory stop-losses. This guide walks you through bringing up the trading stack against a paper (simulated) account, validating it, and the discipline required before you ever consider live trading.

    Read this before you connect a live account

    Autonomous trading places real orders with real money. The setup below is deliberately staged: paper first, manual validation second, supervised autonomy third, and live only after a long, clean soak. Do not skip ahead. Start every deployment in paper mode.

    What the stack contains¶

    When fully wired, trading runs as a small set of containers alongside the swarmd daemon:

    • IB Gateway — IBKR's connection process, kept logged in and restarted daily.
    • Broker sidecar — talks to IB Gateway and exposes simple read/write endpoints on the loopback interface.
    • Broker safety server — fronts the sidecar with the safety envelope (caps, kill switch, mandatory stops) and is the process agents actually call.
    • Technical-analysis helper — computes indicators (SMA, EMA, RSI, MACD, Bollinger Bands, ATR) for strategy agents.

    The deployment ships compose files and make targets to bring these up together.

    Step 1 — enable a paper account at IBKR¶

    1. Log in to your IBKR account settings and request a Paper Trading Account. Approval for retail accounts is usually under an hour.
    2. The paper account shares your live login; a single environment variable selects which session the gateway opens.
    3. Enable always-on two-factor authentication in the IBKR mobile app. Without it, the gateway has to re-authenticate daily and will stall waiting for an interactive 2FA prompt that no one is around to answer.

    Step 2 — stage credentials¶

    Place your IBKR credentials in a secrets file that the stack reads at startup:

    mkdir -p ~/.config/swarmd/secrets
cat > ~/.config/swarmd/secrets/trading.env <<'EOF'
IBKR_USERNAME=your_ibkr_username
IBKR_PASSWORD=your_ibkr_password
TRADING_MODE=paper
EOF
chmod 600 ~/.config/swarmd/secrets/trading.env

    Bring the stack up:

    podman-compose --env-file ~/.config/swarmd/secrets/trading.env \
    -f deployments/podman/trading.compose.yaml up -d

    Step 3 — confirm the connection¶

    Watch the gateway log until login completes, then check the sidecar's health:

    podman logs -f swarmd-ibgateway 2>&1 | grep -i "login"

curl -s http://127.0.0.1:8889/health | jq
# Expect: { "ok": true, "ibkr_connected": true, "account": "DU...", ... }

    A paper account number always begins with DU. If ibkr_connected stays false for more than a few minutes after the gateway reports a completed login, the usual cause is an unanswered 2FA prompt — connect to the gateway's VNC port to check for a waiting dialog.

    Confirm the safety server is up and exposes its tools:

    curl -sS -X POST http://127.0.0.1:8788/message \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | jq '.result.tools[].name'
# Expect: get_account_summary, get_quote, get_historical_bars,
#         get_orders, place_order, cancel_order

    Step 4 — wire it into a project¶

    A project template is provided. Copy it into your deployed configs and edit the watchlist and caps:

    cp configs/projects/trading-paper.yaml.template \
   ~/.config/swarmd/configs/projects/trading-paper.yaml
$EDITOR ~/.config/swarmd/configs/projects/trading-paper.yaml

    The daemon picks up the new project automatically on its next config reload. The template already points the broker tool at the right loopback address.

    Step 5 — validate before letting agents trade¶

    Your account is connected and the stack is healthy. Do not enable autonomy yet. Walk this checklist first — it costs an afternoon and rules out failure modes that look identical to "broken" once a strategy starts running.

    Configure the watchlist and market data¶

    # Append to ~/.config/swarmd/secrets/trading.env, then redeploy:
IBKR_WATCHLIST=AAPL,TSLA,NVDA,SPY,QQQ   # your real watchlist
IBKR_READONLY=true                       # validation only; flip to false later

    Leave the market-data type unset to use the paper default (delayed data). Redeploy with make trading-down && make trading-up.

    Verify reads, then verify writes are blocked¶

    # Reads should return plausible data
curl -s http://127.0.0.1:8889/account/summary | jq '.cash_usd, .equity_usd'
curl -s http://127.0.0.1:8889/quote/AAPL | jq

# With IBKR_READONLY=true, a write must be refused with HTTP 403
curl -sS -X POST http://127.0.0.1:8889/orders \
  -H "Content-Type: application/json" \
  -d '{"symbol":"AAPL","action":"BUY","order_type":"MKT","qty":"1","client_tag":"validate"}'
# Expect: {"code":"readonly", ...}

    Place one tiny order by hand¶

    Flip IBKR_READONLY=false, redeploy, and place a single share to confirm the full round-trip works — the order fills, shows up in the order list, and a far-from-market limit order can be cancelled cleanly. Do this manually before any agent ever sees the place_order tool.

    Confirm the caps actually bite¶

    Set deliberately tiny caps on the broker safety server and try to exceed them — both a single oversized order and a rapid burst of orders. Each should be refused by the safety envelope. These guardrails are what protect you when a strategy agent proposes something it shouldn't:

    SWARMD_BROKER_MAX_POSITION_USD=100
SWARMD_BROKER_MAX_DAILY_TURNOVER_USD=200
SWARMD_BROKER_MAX_ORDERS_PER_HOUR=3

    Survive a forced reconnect¶

    IBKR resets its sessions around midnight. Restart the gateway container and confirm the sidecar reconnects and re-subscribes to the watchlist within about half a minute — this is the daily-restart simulation.

    Run supervised for a day with tight caps¶

    Only after every check above passes, enable the autonomy loop in the project config (trading.mode: paper, trading.killSwitch: false) with tight caps, and review the day's orders and fills at the close. Every fill should have a paired stop and there should be no stuck orders. If anything looks wrong, freeze and investigate before loosening anything.

    Stop-loss enforcement¶

    The safety layer enforces stop-losses deterministically: no opening order, long or short, reaches the broker without a paired protective stop. A strategy agent cannot forget one, and a mistaken "close" on a position you don't hold is correctly recognized as opening a new position and refused.

    Three settings control the behavior on the broker safety server:

    Setting Default Behavior
    SWARMD_BROKER_REQUIRE_STOP_LOSS true Refuse opening orders that have no stop available
    SWARMD_BROKER_DEFAULT_STOP_LOSS_PCT 8.0 Auto-compute a stop this far on the losing side of entry. Tighten toward 3–5% for low-volatility names; loosen for high-volatility ones
    stop_loss_price (per order) agent-supplied An explicit price, which overrides the default percentage

    For an explicit stop price, the side must make sense — below entry for a buy, above entry for a sell — otherwise the stop would trigger immediately and offer no real protection, so it is refused.

    To require an explicit price on every order instead of relying on the auto-default, set the default percentage to 0:

    SWARMD_BROKER_REQUIRE_STOP_LOSS=true
SWARMD_BROKER_DEFAULT_STOP_LOSS_PCT=0   # no auto-compute -> strict

    Entry and stop are placed in sequence, not atomically

    There is a brief window between an entry filling and its stop being submitted. This is acceptable for paper trading and small positions.

    Kill switch¶

    If you need autonomous trading to stop, here are the options from fastest and most surgical to most authoritative:

    1. Project level — set trading.killSwitch: true in the project config. A hot reload picks it up within seconds and refuses all further orders. Orders already open are not cancelled.
    2. Daemon level — set trading.live_enabled: false in the daemon config to refuse all live orders immediately, even if a project is in live mode.
    3. Stack level — bring the trading containers down. The gateway and sidecar stop; any orders already resting at IBKR remain there.
    4. Broker level — log in to IBKR directly and cancel orders and close positions yourself. This is the authoritative stop.

    To clear outstanding orders during normal operation, the sidecar exposes a DELETE endpoint keyed on the order's tag; cancels are idempotent, and cancelling a parent order also cancels its child stop.

    Live promotion¶

    Going live is mechanically one line of config. Treat it as the most consequential change you will make. Before flipping it:

    • Run continuously in paper for an extended soak (on the order of two weeks).
    • Confirm the strategy's quality and verification checks have been clean over that period.
    • Start live with very tight caps and hold them there for at least two weeks before raising anything.

    Size every cap — per-position dollars, daily turnover, position count — to the actual capital in the account, not to defaults or paper figures. Paper accounts start with a large simulated balance that bears no relation to a real account; re-derive every limit from your real numbers before going live.

    A note on market data¶

    A paper account uses delayed market data by default. Some IBKR pre-trade risk checks reject orders priced against a delayed feed, which shows up as orders that cancel themselves without filling. If you see this, you can have the safety layer refuse such orders up front rather than churning through them:

    # ~/.config/swarmd/secrets/trading.env
SWARMD_BROKER_REFUSE_DELAYED_QUOTES=true

    Once you subscribe to real-time market data, set it back to false (the default) and confirm a quote reports it is no longer delayed.
